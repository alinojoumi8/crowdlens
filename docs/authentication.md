# Invitation and OIDC sign-in

`AUTH_MODE=local` preserves the existing single-operator application; it is not an authentication boundary and must remain loopback-only. `AUTH_MODE=oidc` enables a global request gate before other application middleware. Invalid/incomplete OIDC configuration fails startup rather than falling back to local mode.

Configure a maintained OIDC identity provider with authorization code + S256 PKCE, signed ID tokens, `openid email`, verified email and admin MFA. Set a random SECRET_KEY of at least 32 characters, AUTH_BASE_URL (the canonical application origin), AUTH_ISSUER, AUTH_CLIENT_ID, AUTH_CLIENT_SECRET and AUTH_ADMIN_EMAIL. AUTH_ISSUER must match the provider discovery document's issuer exactly, including any trailing slash. Register exactly `AUTH_BASE_URL/auth/callback`. Production URLs must be HTTPS. Forwarded/Host headers do not determine the callback URL. The configured provider must emit `amr: ["mfa", ...]` for administrators; do not fake that claim or disable this requirement. Test actual provider recovery and MFA before external use.

AUTH_DB_PATH defaults to `backend/uploads/auth.db`; an empty environment value uses the default. Preserve this database in coordinated backups, restrict host access and keep credentials out of source control. Identity is keyed by issuer+subject, not silently linked by email. The configured administrator is bootstrapped on its first verified MFA sign-in. Changed subjects/emails require operator handling; they never silently take over an existing account. Tester roles cannot be promoted via request parameters.

Admin account page: create a tester invitation code, deliver it through an authorized private channel, suspend/reactivate testers. No SMTP integration or automated sending is implied. Codes expire in 24 hours, are consumed transactionally and are bound to verified email. Issuing a new code for the same email revokes the previous one.

Sign-in uses Authlib token validation, nonce/state and PKCE. CrowdLens stores no provider password or access/refresh token. Local opaque sessions are server-revocable, expire after eight hours or 30 minutes idle, and are replaced at sign-in. Sign out ends the CrowdLens session; sign out all devices revokes all that account's CrowdLens sessions. Provider sessions/recovery remain at the IdP, and every new sign-in requests provider authentication. Suspension immediately invalidates existing local sessions.

In OIDC mode, anonymous API/download requests receive 401; page requests go to sign-in. Tester accounts can access their account/session actions only. Application routes remain admin-only until B08 administrator-owned quotas are implemented. B07 workspace authorization also applies to administrators; an administrator cannot browse another account's resources. See [workspace ownership](workspace-ownership.md). State-changing authenticated operations require the session CSRF token. The built frontend uses same-origin cookies; cross-origin authenticated frontend deployment is not supported by this slice. The health endpoint is public for local orchestration.

For development, `/auth` is proxied with `/api`. Set AUTH_BASE_URL to the Vite frontend origin (for example, http://localhost:3000), and register that origin's `/auth/callback` at the IdP. Use explicit AUTH_ALLOW_HTTP_LOOPBACK=true only for loopback test apps; it does not authorize public HTTP. `backend/tests/oidc_test_provider.py` signs fixture tokens and lets tests select identities without passwords. It binds only to 127.0.0.1 and is NOT a real authentication provider. Never run it for real users.

Verification must include anonymous access, admin/tester boundaries, CSRF, invitation replay/expiry/wrong email, callback state/nonce/audience/issuer validation, session expiry/revocation and suspension, and second-browser sign-in after simulated provider recovery. Synthetic recovery proves the client can return with the same subject, not the recovery security of an unconfigured provider.

## Local verification, 2026-10-18

The isolated loopback provider exercised actual authorization-code exchange, PKCE and signed ID-token validation. `pnpm check` passed 1,094 backend tests (including 15 authentication tests), 12 frontend unit tests, 110 component tests and the production build. Lint/typecheck scripts are not configured. Chromium checks covered admin sign-in, invitation creation and tester sign-in, tester API denial, sign-out-all, suspension/reactivation, public notice access, keyboard focus, narrow-screen layout and the built frontend's account link. The fixture omits business APIs, so its home-page readiness/history errors are expected; it is not a full application workflow acceptance run. Provider-managed recovery was simulated with a second client and the same subject, not verified against a real identity service. No model requests were made. The existing deployed application and its stopped 45/60 allowance were preserved.
